# Longhorn 1.13.0 upgrade: version-matched upstream review

Reviewed 2026-10-18 UTC against official version-tagged documentation and source. Actual cluster, networking, engine and SystemBackup evidence is recorded in [the alignment report](longhorn-engine-alignment-20261018.md).

## Upgrade path and compatibility

The version-matched manager procedure explicitly supports manager upgrades from **1.12.x to 1.13.0** and engine live upgrades from **1.12.x to 1.13.0**. Flux users update `spec.chart.spec.version` in their existing HelmRelease. Volume backups are a stated prerequisite. StorageClass parameters must retain their existing values so immutable-field changes cannot break the Helm upgrade. Manager rollout and engine upgrades are separate stages. Successful downgrade is unsupported. [Manager upgrade](https://longhorn.io/docs/1.13.0/deploy/upgrade/longhorn-manager/), [upgrade overview](https://longhorn.io/docs/1.13.0/deploy/upgrade/).

The release requires Kubernetes **1.34 or later**, because external-provisioner becomes **6.3.0**. All-V1 deployments do not need the V2-only detach prerequisites: V2 live upgrades specifically need 1.12.2, whereas V1 remains supported from 1.12.x. Review failed BackingImages and faulted volumes before proceeding. [Release notes](https://github.com/longhorn/longhorn/releases/tag/v1.13.0), [manual pre-upgrade checks](https://longhorn.io/docs/1.13.0/deploy/upgrade/#manual-checks-before-upgrade).

The exact chart pins CSI attacher 4.13.0, provisioner 6.3.0, resizer 2.2.1, snapshotter 8.6.0, node-driver-registrar 2.18.0 and liveness-probe 2.20.0. Compare rendered objects and the current installation rather than treating these as independently chosen updates. [1.13.0 chart values](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/values.yaml).

The chart CRD templates grow from **25 to 28** CRDs: added `instancemanagerupgradecontrols.longhorn.io`, `instancemanagerupgrades.longhorn.io`, `snapshotgroups.longhorn.io`; none removed. All declared versions in both templates remain **v1beta2**, served and storage. This is a source comparison, not proof that the live CRD storedVersions and Flux Helm CRD policy are correct; verify those independently. [1.12.1 CRDs](https://github.com/longhorn/charts/blob/longhorn-1.12.1/charts/longhorn/templates/crds.yaml), [1.13.0 CRDs](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/templates/crds.yaml).

## Global Manager

The new `longhorn-global-manager` Deployment owns cluster-wide Pod and PV controllers. Defaults: **three replicas**, one elected leader and two standbys; preferred node anti-affinity; no default resource requests/limits; no default node selector/tolerations. Upstream's minimum preflight is one schedulable Pod. This three-node homelab should require **3/3 available** after rollout and verify node placement. The chart uses `longhorn-service-account`, manager 1.13.0 image, and readiness/liveness HTTP **`/v1/healthz` on 9505**. [Important notes](https://longhorn.io/docs/1.13.0/important-notes/#longhorn-global-manager), [Deployment template](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/templates/deployment-global-manager.yaml), [chart values](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/values.yaml).

## CSI Secret access

Retain **`csi.allowControllerSecretAccess: false`**. With false, Helm omits `longhorn-csi-secret-role` and `longhorn-csi-secret-bind`; the dedicated CSI account's base role is Secret-free. Inspect Longhorn StorageClasses for historical `csi.storage.k8s.io/provisioner-secret-*` and any custom controller-side Secret requirement. Node-side PV references are a separate boundary and do not justify granting controller Secret access. Do not modify production PVs, encryption keys or Secret contents merely to satisfy this gate. [Version-matched Secret restriction and migration notes](https://longhorn.io/docs/1.13.0/important-notes/#optional-restriction-of-csi-controller-secret-access).

## Instance-manager TCP/3260 policy

Exact field: **`networkPolicies.v1DataEngineInitiatorSourceCIDRs`** (list of CIDR strings). The instance-manager ingress template adds TCP/3260; when the list is empty the rule has **no `from` restriction**. When populated, it emits an `ipBlock.cidr` peer per entry. Existing same-namespace manager/instance-manager/backing-image-manager/data-source selectors still allow their component communication. `restrictInternalTraffic` defaults true, independently of outer ingress-policy `enabled`. [Exact template](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/templates/network-policies/instance-manager-networking.yaml), [values](https://github.com/longhorn/charts/blob/longhorn-1.13.0/charts/longhorn/values.yaml).

Upstream requires **effective sources observed by the CNI**, not an assumed node or Pod subnet. Existing established connections can hide fresh-connection policy errors. kube-network-policies **v1.1.0** queues traffic at POSTROUTING priority **SNAT−5**, explicitly before SNAT; it also bypasses root-owned host sockets, so the resulting policy cannot be claimed to constrain every host-root actor. Flannel **v0.28.8** has host-to-overlay masquerade rules. Therefore target `/proc/net/tcp` peers should be paired with actual host-network route-source evidence before choosing CIDRs; do not automatically add full Pod/LAN ranges or all node IPs. A read-only `ip route get <local instance-manager PodIP>` in an existing hostNetwork networking Pod can verify selected source addresses without direct Talos access. [kube-network-policies dataplane](https://github.com/kubernetes-sigs/kube-network-policies/blob/v1.1.0/pkg/dataplane/controller.go#L521-L531), [host-root bypass](https://github.com/kubernetes-sigs/kube-network-policies/blob/v1.1.0/pkg/dataplane/controller.go#L630-L644), [Flannel masquerade](https://github.com/flannel-io/flannel/blob/v0.28.8/pkg/trafficmngr/iptables/iptables.go#L137-L168).

## SystemBackup while still running 1.12.1

Supported `longhorn.io/v1beta2` SystemBackup `spec.volumeBackupPolicy` choices: **`if-not-present`** creates missing/outdated volume backups, **`always`** backs up all volumes, **`disabled`** creates no volume backups. A ready protection point requires **`status.state: Ready`**; the default backup target stores it. The bundle contains Longhorn-operated objects including PV/PVC/Volume, not arbitrary application Pods or Longhorn Node resources. It is not full application or cluster recovery. [1.12.1 procedure](https://longhorn.io/docs/1.12.1/advanced-resources/system-backup-restore/backup-longhorn-system/).

Implementation detail relevant to policy selection: `if-not-present` first creates a volume snapshot, then checks the previous backup and snapshots for newer nonzero-sized data. Missing last backup/snapshot is stale; a newer nonzero snapshot makes it stale. It may therefore generate more backups than merely the five unbacked new volumes. This policy is suitable if reusing current backups is deliberate, while **`always`** is the straightforward choice for a fresh pre-upgrade point across all volumes when capacity and I/O permit. Ready follows successful resource bundle upload, after waiting for generated volume backups to complete and synchronize into `volume.status.lastBackup`. Independently require completed recent backups for every current production volume; never infer that from `Ready` alone. [1.12.1 SystemBackup controller](https://github.com/longhorn/longhorn-manager/blob/v1.12.1/controller/system_backup_controller.go#L745-L980).

## Patch engine alignment while manager stays 1.12.1

The 1.12.1 documentation's 1.11.x example does not make same-minor patch engine alignment unsupported. The version-tagged native API calls `VolumeManager.EngineUpgrade`; it checks V1, image readiness on attachment/replica nodes, no conflicting upgrade/migration, healthy attached state and non-strict-local attachment. It contains no minor-version-only restriction. The volume controller additionally checks old/new EngineImage readiness, distinct GitCommit (unless explicit same-commit revision setting permits), and controller API compatibility. Verify these actual EngineImage fields; never enable the same-commit override to force an unsupported change. Native HTTP acceptance alone is not completion. [Native API](https://github.com/longhorn/longhorn-manager/blob/v1.12.1/api/volume.go#L820-L841), [manager gates](https://github.com/longhorn/longhorn-manager/blob/v1.12.1/manager/volume.go#L844-L927), [live controller compatibility](https://github.com/longhorn/longhorn-manager/blob/v1.12.1/controller/volume_controller.go#L4794-L4831).
